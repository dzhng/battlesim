1. Known knowns

  • The city-maps follow-up is personal tuning of generation business rules with regenerated maps and measurements, using the existing generator. UI, saving and hot reload were expressly deferred. Generation report.
  • The same generator accepts supplied preset, template and resolved physical-rule documents per call. An unsaved draft can be previewed without changing production sources. It already exports both complete plans and compiled maps to Wasm. Wasm boundary.
  • Rust validates presets. Its plan measurement owner calculates land coverage, fairness, roads, transit and approaches; its SVG inspector draws plan layers and detailed crops. These are reusable owners, not a reason to recreate generation or geometry checks in TypeScript. Preset validator; Measurements; Inspector.
  • Open, Mixed and Metro remain separate from Small, Medium and Large (6/8/10 km). This walk does not add hills, new art families, arbitrary map dimensions, hand-painted map geometry or combat tuning. City-maps rationale.
  • A seed is canonical u64 decimal text, never a JavaScript number. Requests pin generator/preset versions and physical templates. Config and map hashes have their existing meanings; appearance identity stays separate. Request; Identity owner.
  • The continuous physical sight certificate is generation admission. Sampled infantry openness is a separate diagnostic/report policy. Neither a plan image nor that sampled percentage proves all-position coverage, actual travel or battle outcomes. Coverage and sight meanings.
  • The mechanics editor supplies a local draft → authoritative validation → exact save diff → stale-source rejection precedent. Its unit-inheritance store is specific to mechanics and should not become the map editor's store. Mechanics workflow; Preview and save.

3. Unknown knowns — context extracted

  • Inspection preference: the user selected the plan instead of a rendered game view. Prioritize causal geometry: where districts, roads, parcels and furnishings come from.
  • Navigation preference: the user reacted to an apartment-district example and selected both control search and map-driven navigation. Both routes must identify the same rule, with its scope clear.
  • Definition of useful tuning: one appealing seed is insufficient. The user selected an on-demand multi-seed sample as well as individual inspection.
  • Different audiences: a developer can use a refused seed and its diagnostics to tune policies. A player pressing Play needs a battle and cannot repair generator settings. The user explicitly rejected the existing failure screen as the normal outcome.
  • Environment/consumer: the inherited purpose is personal local tuning, and saving to checkout fixture defaults was explicitly chosen. Solo localhost usage remains the stated assumption; remote collaborative editing has not been requested.
  • Scope amendment: the user asked for validator tunables too. Numerical quality policies are therefore not permanently frozen just because city-maps shipped initial requirements. Physical correctness retains its own authority.

The concrete example used actual apartment defaults: 130 m block depth, 230 m length, 20% cross-street omission and an 85:15 apartment/attached-home mix. Trial changes were explicitly illustrative, not generated results.

DECIDED · PLAYER RECOVERY

Returning to the menu can request the same failed seed

Evidence: the battle route advises deploying again for another map, but passes the original choice into its menu return link; the menu reuses a supplied seed. The preparation worker reports refusal and closes, with no recovery selection.

Why it bites: the player's suggested recovery can reproduce exactly the same failure.

Task change: ordinary Play gains automatic admitted-battle selection and bounded fallback. This user-added requirement is implemented; the final rationale records its bounded selection contract.

RESOLVED · MUTABLE CAPACITY

Generation and saved-map admission have matching limits in two places

Evidence: generation reads limits from fixtures/generated-battle.json, while MapAdmission::CATALOGUE compiles matching 60,000-part and 600,000-bay limits into Rust; both native and Wasm catalogue readers use that constant.

Why it bites: a fixture-only edit can drift from catalogue admission and its equality check. Lowering a budget must also not accidentally destroy the promised Play fallback.

Task change: define the relationship between editable generation work policy, released-map admission and fallback before enabling these controls. One publication must keep the intended shared constraints coherent.

RESOLVED · 500 MS PERFORMANCE CONDITION

The sight report is not yet a production browser API

Evidence: the shared calculation lives under mapgen examples and uses simulation queries; sim is a mapgen dev-dependency. Browser generation output has compile counts and sites, rather than the detailed sight report.

Why it bites: native source availability does not prove a browser result or a sub-500 ms cost. Moving simulation work into the production mapgen crate would violate its current boundary.

Task change: expose one simulation-owned analysis calculation, reuse it in reports/tests and workbench, then measure the full additional work in the actual execution path. Until that gate is proven, sight remains on demand.

SHARP EDGE · LIVE DOES NOT MEAN INSTANT

Large generation already takes seconds

Evidence: the retained current-art Metro Large seed 4 browser record measured roughly 4.1–4.2 seconds for map generation and 2.3 seconds for encounter preparation; first playable view was roughly 15 seconds. This is historical evidence for one identified map, not a new workbench timing result.

Why it bites: starting a job per keystroke, restarting indefinitely or repeatedly trying the same failed request can waste substantial work without progress.

Task change: keep bounded latest-draft scheduling, visible pending state and cancellation. Retry selection changes the candidate seed and preserves the existing under-30-second startup requirement; its budget needs measured fallback headroom.

DECIDED · IDENTITY AND SNAPSHOTS

A seed and revision label alone do not reproduce an edited draft

Evidence: the request contains no draft ID or editable-value payload; current config identity hashes physical input identity and the final plan. Version labels alone are not verified source provenance.

Why it bites: an old preview, a batch report and newly saved defaults can otherwise appear to describe the same settings.

Task change: bind every result to the exact input snapshot, source revision, type/size/seed and existing output identity. Preserve tested inputs with a report. Do not call a source-content fingerprint the current map/config hash.

DECIDED · INSPECTOR REUSE

The inspector exists, but interactive inspection needs an exposure seam

Evidence: the Rust SVG inspector supports whole-map and settlement/district/bridge crops, with detail selected from view width. Existing Wasm exports plans and compiled maps, not this interactive inspection contract.

Why it bites: a separate TypeScript geometry implementation or a second generator would make the diagram disagree with the game. Browser zooming a static overview does not itself add detail that Rust omitted.

Task change: extend/expose the existing inspection owner with layers, selection metadata and detailed views from the same generated result. Keep pan/zoom and selection separate from regeneration of unchanged inputs.

RESOLVED · SOURCE POLICY INVENTORY

The frozen list mixes policies with numerical safeguards

Evidence: the appendix records 699 preset leaves and 76 source constants, explicitly including different roles. Bowed-street shaping uses source constants; the physical certificate separately has a 512,000,000-operation envelope. Deleted proximity-sight knobs are not future controls.

Why it bites: exposing every constant alike can turn a proof assumption into an apparent quality slider, or miss a genuine business-rule control.

Task change: classify the complete inventory before field implementation, identify every promoted field's owner, and preserve initial numerical behaviour during extraction. The historical city-maps appendix stays a frozen reference, not live configuration.
