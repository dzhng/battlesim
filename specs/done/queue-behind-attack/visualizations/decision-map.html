Queue behind an attack: the map

You can now shift-queue a move (or anything else) behind an attack or attack-ground, for every unit, and the Space view shows the chain. Part 1 is the sim, the contract and ground units' overlay; part 2 is the jets' 3D attack line. Paths are relative to the battlesim worktree.

Contract changes first
  • Order admission: a queued Move, AttackMove or Unload to a point behind an Attack is placed (it used to come back unplaced and be dropped without a word). The "queued move behind an indefinite attack" case of NoValidDestination goes away. The Order and CommandEnvelope shapes don't change.
  • Own-unit observation: OwnUnit.queue: [x,y][] and queue_unloads: bool[] are replaced by one ordered list of steps. Each step is move {point, unloads} or attack {target kind and id from the targetKinds table, plus a point}. The current order's attack target is published the same way. goal still means the chase point. There's no compatibility shim.
  • Publication layout: the own-unit row and queue section change shape. The codec vectors are hand-edited, the stream hashes re-blessed, and the parity captures recorded again once. The server and web deploy together, because an old client rejects the new layout.
  • Battle digest: unchanged for every battle that never queues behind an attack, including the skirmish AI, encounters and endurance runs, which never do. The new progress state is added to the digest only when present.
  • Every queued order is a step: move, attack, garrison, board, collect, unload, exit and return to base (decision 15).

Q1Known knowns: settled ground

  • Where the refusal lives: the after_attack check in crates/sim/src/battle/move_placement.rs:181. apply_units then skips the unplaced queued move (crates/sim/src/battle.rs:2932). It was introduced in e5d49dc7c, and the move-validity spec records it (specs/done/move-validity/README.md:14, choices.md:37).
  • Which orders it hits: only Move, AttackMove and Unload to a point, through place_move (battle.rs:2763-2807). Garrison already plans a queued order from the last move's end (crates/sim/src/garrison/occupy.rs:102). Board, Collect and Refund are never refused.
  • The client already sends shift-click as queued: true for every order (web/src/battle/input/pointerIntent.ts:158). Only the sim refuses.
  • Attack-ground never ends for any unit (battle.rs:2574, crates/sim/src/air/orders.rs:65).
  • The Space view is the order overlay (buildOrderOverlay, which also flashes after an order is issued; web/src/battle/present/orderReveal.ts). Jets get no marker, no route and no goal circle, only a ghost and drop line at the end of their orders (packages/battle-renderer/src/unitCircle.ts:114, orderOverlay.ts:662,678).
  • No test pins the refusal.
