# Frame cost

One row per slice: 1920×1080 on this Mac (M5 Pro, hardware Metal, Chromium). No budget until slice 27 (30 FPS floor at the default camera).

**Method.** Rows 00–09 (and spike 01) used slice 00's `village-perf` probe, now deleted. **From slice 10 on, every row is the benchmark's short run**: `bun run --cwd web scene -- benchmark` on the production build, holding the GPU lock (`throwaway/gpu.lock`). The scene writes the row to `throwaway/evidence/benchmark/frame-cost-row.md` and the full JSON report beside it. The run is the `village-contact` scenario: the village warm-started to tick 6300 (heavy contact), blue on the supported script, red the defender, 60 s of the camera tour through strategic, pan, zoom, ground, combined and return, redrawn every frame. GPU is `BattleFrame.stats().gpu` (slice 12): the `timestamp-query` frame total over the frame's last 240 frames, read every 2 s and attributed to the phase it was read in. The row gives the mean of those readings, the worst window p95, and each phase's mean. Apple's GPU overlaps passes, so there is no per-pass split. Buffer and texture bytes are the frame's sized allocations at the end of the run. Rows name the scenario and tour version: compare rows only across the same version.

**Repeatability (slice 10).** Two short runs back to back under the GPU lock, on a heavily loaded machine (load 21–26, parallel agents): p50 8.33/8.33 ms, p95 8.93/9.07, p99 9.25/9.28, GPU frame mean 2.34/2.13 ms (worst window p95 4.35/5.79). Stated tolerance: frame percentiles within 0.2 ms, GPU frame mean within 10 %; beyond that is a change, not noise. The worst-window GPU p95 is noisy under load and is not a comparison number.
